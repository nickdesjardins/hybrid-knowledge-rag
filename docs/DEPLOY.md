# Putting the showcase online, step by step

Everything here runs on free plans. Five steps, about 45 minutes, most of it waiting for builds.

| What | Where | Address |
|---|---|---|
| The **project page**: recorded runs, the walkthrough, wakes the demo | GitHub Pages | `https://nickdesjardins.github.io/hybrid-knowledge-rag/` |
| The **live demo**: the API with its playground at `/` | Render (free web service, Docker) | `https://<service>.onrender.com/` |
| The **database**: PostgreSQL with pgvector, already filled | Neon (created from Vercel) | not public |
| The **language model** | OpenRouter free models | not public |

The project page is the address to give to people. The live demo sleeps after 15 minutes without
a visit and needs about a minute to wake; the project page starts waking it as soon as it opens.

## Where each secret goes

| Secret | GitHub | Render | Your computer |
|---|---|---|---|
| OpenRouter key | **never** | `OPENROUTER_API_KEY`, typed once in step 3 | `.env.local` |
| Neon connection string (`DATABASE_URL_UNPOOLED`) | **never** | `DATABASE_URL`, typed once in step 3 | `.env.local` |
| Upload key (`API_KEY`) | **never** | generated by Render, nothing to type | not needed |

GitHub needs **no secrets at all**: the two workflows (tests and the project page) use none.
Never paste a key into `render.yaml`, a commit, a chat or a terminal command.

## Step 1: put the code on GitHub (5 minutes)

The repository `github.com/nickdesjardins/hybrid-knowledge-rag` already exists (public, empty),
and this folder is already connected to it over SSH. Nothing to create, nothing to configure.

In PowerShell, in the project folder:

```powershell
git add -A
```

Check that no private file is about to be published. The only line printed must be
`.env.example`:

```powershell
git ls-files | Select-String -Pattern "env|Career"
```

If `.env.local`, `.env` or the career guide appears, stop and ask for help before going on.
Otherwise:

```powershell
git commit -m "Hybrid retrieval engine with public showcase"
```

```powershell
git push -u origin main
```

## Step 2: turn on GitHub Pages (5 minutes)

1. Open <https://github.com/nickdesjardins/hybrid-knowledge-rag>, then **Settings** (top bar of
   the repository), then **Pages** in the left sidebar.
2. Under **Build and deployment > Source**, choose **GitHub Actions**. GitHub then suggests
   workflow templates: **ignore them**. The project already has its own
   (`.github/workflows/pages.yml`), and a template would add a second one.
3. Open the **Actions** tab. The run called **Project page** most likely failed with "Get Pages
   site failed", because it started before step 2. That is expected. Open the run, click
   **Re-run jobs > Re-run all jobs**. (Or: **Project page** in the left list, **Run workflow**,
   branch `main`, **Run workflow**.)
4. When it turns green, open <https://nickdesjardins.github.io/hybrid-knowledge-rag/>. The first
   time can take a few minutes. The page shows the recorded runs and says "The live demo is not
   online yet". That is correct until step 4.
5. The **Tests** run should be green too. Yellow notes that mention "Node.js 20" are warnings
   from GitHub, not failures.

## Step 3: create the live demo on Render (20 minutes, mostly the first build)

Before you start, open `.env.local` in an editor (VS Code or Notepad). You will copy two values
from it. Copy only the part after the `=` sign, without quotes.

1. Go to <https://dashboard.render.com> and sign in (the same account as Phase 1 is fine).
2. Click **New > Blueprint**.
3. Find `hybrid-knowledge-rag` in the list and click **Connect**. If it is not in the list,
   Render's GitHub app is not allowed to see it yet: follow Render's link to configure GitHub
   access (or open <https://github.com/settings/installations>, **Render > Configure**), add
   `hybrid-knowledge-rag` under repository access, save, and come back.
4. **Blueprint name**: anything, for example `hybrid-knowledge-rag`. **Branch**: `main`. Leave
   **Blueprint path** empty.
5. Render lists what it will create: **one web service, `hybrid-retrieval-engine`, plan Free**.
   Check that it says Free. Render may ask for a card to verify the account (a $1 charge that is
   refunded); you do not need to add one otherwise, and without a card Render pauses instead of
   billing if a free limit is ever exceeded.
6. Fill in the two boxes Render shows. It asks for them **only this once**:
   - `OPENROUTER_API_KEY`: the value of `OPENROUTER_API_KEY` from `.env.local`;
   - `DATABASE_URL`: the value of **`DATABASE_URL_UNPOOLED`** from `.env.local` (it starts with
     `postgresql://` and has no `-pooler` in it). Not the line called `DATABASE_URL`.
7. Click **Deploy Blueprint**. The first build takes about 10 minutes: it installs Python
   packages and downloads the two local models into the image. Follow it on the service's
   **Events** and **Logs** pages. Wait until the status says **Live**.
8. Copy the address at the top of the service page. It is
   `https://hybrid-retrieval-engine.onrender.com`, or the same with a few extra letters if that
   name was already taken by someone else.
9. Check it, replacing `<service>` with that address:
   - `https://<service>.onrender.com/livez` shows `"status": "alive"`;
   - `https://<service>.onrender.com/health` shows `"status": "ok"` and
     `"database_connected": true`;
   - `https://<service>.onrender.com/` opens the playground. Click a sample question, then
     **Ask**. The answer takes 10 to 40 seconds; open **Walk through this answer** under it.
10. Optional check that visitors are told apart: ask 11 questions within a minute from your
    computer, and the 11th says "Too many questions from this address". Then ask one from your
    phone on mobile data, not Wi-Fi: it must be answered. If the phone is refused too, every
    visitor shares one budget. The demo is still safe; see [Troubleshooting](#troubleshooting).

If you typed a value wrong in step 6: service page > **Environment** > edit the value >
**Save and deploy**.

## Step 4: link the project page to the live demo (3 minutes)

1. Open `site/index.html` and search for `hybrid-retrieval-engine.invalid` (it appears once).
2. Replace `hybrid-retrieval-engine.invalid` with the host from step 3.8, so the line reads, for
   example, `href="https://hybrid-retrieval-engine.onrender.com/#ask"`. Keep `https://` before
   it and `/#ask` after it.
3. Publish it:

   ```powershell
   git add site/index.html
   ```

   ```powershell
   git commit -m "Link the live demo"
   ```

   ```powershell
   git push
   ```

4. The **Project page** workflow runs again (Render does not rebuild for a change in `site/`).
   Reload the project page: it says "Waking the live demo", then "The live demo is awake".

## Step 5: replace the OpenRouter key (5 minutes)

The current key appeared in a tool output during development, so replace it now that
everything works.

1. On <https://openrouter.ai/keys>, create a new key and copy it.
2. Render: service page > **Environment** > `OPENROUTER_API_KEY` > edit > paste >
   **Save and deploy** (no rebuild needed).
3. Put the new key in this project's `.env.local`.
4. Phase 1 uses the same key: update it in its `.env`, in its Render service (**Environment**),
   and in its GitHub repository secret (**Settings > Secrets and variables > Actions**).
5. Back on <https://openrouter.ai/keys>, delete the old key.
6. Ask one question on the live demo to confirm it still answers.

## Good to know about the free plans

- **Sleeping.** The demo sleeps after 15 minutes without a visit and takes about a minute to
  wake. The project page wakes it automatically.
- **Builds cost minutes.** Render gives 500 build minutes a month; one build of this image takes
  about 10. A push that changes only `site/`, `docs/`, `README.md`, `.github/`, `tests/` or
  `scripts/` does not rebuild the service. Group other changes into fewer pushes.
- **Change settings in `render.yaml`, not in the dashboard.** For every setting that
  `render.yaml` lists with a value, edit the file and push: a later Blueprint sync can put the
  file's value back over a dashboard edit. The dashboard is the place only for
  `OPENROUTER_API_KEY`, `DATABASE_URL`, `API_KEY`, and settings the file does not list.
- **Fixed once created.** The region (Virginia, next to the Neon database in us-east-1) and the
  `onrender.com` address cannot be changed later.
- **Hours.** A workspace gets 750 free instance hours a month, shared by all its free services
  (Phase 1 included). Sleeping services use none.

## What protects the public demo

| Risk | Protection |
|---|---|
| Someone uploads documents | Uploads need `API_KEY`. The key and the size are checked before a byte of the upload is read. |
| Someone spends the day's free requests | Per visitor: 10 questions a minute and 60 a day. Everyone together: 20 a minute and 800 a day. And the service asks OpenRouter for the real count once a minute and stops at a reserve (50, or a fifth of the day's allowance if that is smaller). |
| Someone pretends to be many visitors | The address comes from `CF-Connecting-IP`, which Cloudflare (in front of every Render web service) overwrites; the left-most `X-Forwarded-For` entry, which a client can write, is never used. IPv6 visitors are grouped by their /64 network. |
| Someone floods the small instance | At most 4 questions are answered at once (more get 503 with `Retry-After`), questions are capped at 500 characters, every other request body at 32 KB, and the local models run one call at a time. |
| A typo makes the service call a paid model | `OPENROUTER_FREE_ONLY=true` refuses any model id that does not end in `:free`, at start-up. |
| A document tells the model what to answer | Passages are wrapped in tags with a random suffix per request, and declared untrusted. Every quote is checked against the stored text. |
| An error message leaks a key, a quota or SQL | Clients get the provider's name, "temporary" or "permanent", and an incident id; a database failure is a 503 with an incident id. Validation errors never echo the rejected input, and a bad setting is reported without its value. The detail stays in the log. |
| The corpus contains something private | The corpus is four fictional documents written for the demo (`scripts/make_demo_corpus.py`). |

Free endpoints may keep and train on what they are sent. Do not ingest real compliance documents
while the service runs on free models.

## Day-to-day

**Add a document to the live demo.** The key is `API_KEY` in Render's dashboard (service page >
**Environment**). Keep it out of command lines, which shells save in their history: read it into
a variable for the session.

In PowerShell (Windows), paste the key at the prompt; what you type at a `Read-Host` prompt is
not saved in the history:

```powershell
$env:DEMO_API_KEY = Read-Host "Upload key"
```

```powershell
curl.exe -X POST https://<service>.onrender.com/api/v1/ingest -H "X-API-Key: $env:DEMO_API_KEY" -F "file=@my-document.pdf" -F "title=My Document"
```

In bash (macOS, Linux, Git Bash):

```bash
read -rs -p "Upload key: " DEMO_API_KEY
```

```bash
curl -X POST https://<service>.onrender.com/api/v1/ingest -H "X-API-Key: $DEMO_API_KEY" -F "file=@my-document.pdf" -F "title=My Document"
```

Use `curl.exe`, not `curl`, in Windows PowerShell 5.1: there `curl` is an alias of another
command that does not take these options.

**Keep the demo awake (optional).** An uptime monitor (UptimeRobot, cron-job.org) can request
`https://<service>.onrender.com/livez` every 10 minutes so visitors never wait for a cold start.
Point it at `/livez` only: it never touches the database, so Neon still suspends and its free
compute allowance is not spent. One service awake all month uses about 730 of the 750 free
instance hours a workspace gets, so do this for one service at most.

**Change the sample corpus**: edit `scripts/make_demo_corpus.py`, then

```powershell
.\.venv\Scripts\python.exe scripts\make_demo_corpus.py
```

```powershell
.\.venv\Scripts\python.exe scripts\record_runs.py --reseed
```

The second command replaces the sample documents in the database and records the runs again
(seven free requests). Commit `demo/` and `site/recorded/runs.json` and push.

**Run the showcase on your own machine**, exactly as Render runs it:

```powershell
.\.venv\Scripts\python.exe scripts\run_local_demo.py
```

**Check the key and the model chain** (one or two free requests):

```powershell
.\.venv\Scripts\python.exe scripts\openrouter_smoke.py
```

## Troubleshooting

| What you see | What it means | What to do |
|---|---|---|
| The repository is missing under **New > Blueprint** | Render's GitHub app cannot see it | GitHub > **Settings > Applications > Render > Configure** > add the repository. |
| Render asks for payment information | Usually a service that is not on the Free plan; sometimes an account check | Check that the service shows **Free** (`plan: free` in `render.yaml`). A verification charge of $1 is refunded. |
| Render: "Ran out of memory (used over 512MB)" | Both local models plus the service did not fit | In `render.yaml`, set `RERANK_PROVIDER` to `none` and push (frees about 100 MB; passages then keep their fusion order). |
| The build fails at the `RUN python -c "from fastembed ..."` line | Hugging Face did not answer during the build, or its download cache was not writable | Use **Manual Deploy > Clear build cache & deploy**. If the log mentions `xet` or a permission error, add `HF_HUB_DISABLE_XET=1` to the `ENV` block of the `Dockerfile` and push. |
| The deploy fails; the log shows "Database not ready" several times, or "must be a PostgreSQL connection string" | `DATABASE_URL` is empty (the service then tries a database on its own machine) or not a connection string | Service > **Environment** > `DATABASE_URL`: paste the `DATABASE_URL_UNPOOLED` value from `.env.local`, then **Save and deploy**. |
| `/health` says `"status": "degraded"` with `generator.configured: false` | `OPENROUTER_API_KEY` is missing or empty | Service > **Environment**: set it, **Save and deploy**. |
| `/health` answers 503, or questions answer 503 "The database is unavailable" | The database cannot be reached. Right after a long idle period Neon may still be resuming. | Retry after a few seconds. If it persists, check `DATABASE_URL` and the Neon dashboard. The log line carries the incident id from the message. |
| Questions answer 503 "The demo is answering other questions" | Four questions were already being answered | Nothing to fix; the page shows when to retry. |
| `/livez` answers but `/` does not load | The service started but the playground is off | Check `PLAYGROUND_ENABLED` (true by default). |
| Start-up fails with `document_chunks.embedding is vector(384) but EMBEDDING_DIMENSIONS=...` | The database was filled with another embedding width | Keep `EMBEDDING_DIMENSIONS=384`, or empty the tables and ingest again. |
| Every question answers 502/503 "Upstream provider error (openrouter)" | Both free models failed, or both were withdrawn | Run `scripts/openrouter_smoke.py`: it says which models OpenRouter still lists. Set working `:free` ids in `OPENROUTER_MODELS` (service > **Environment**; `render.yaml` does not list it). |
| Questions answer 429 | A limit was reached | The message says which one and `Retry-After` says when. The limits are the `QUERY_*` lines of `render.yaml`. |
| Your phone on mobile data is refused after your computer hit its limit | Render did not pass `CF-Connecting-IP`, so all visitors share one budget | The demo stays safe (that is the stricter failure). Ask Render support which header carries the client address, and set it as `CLIENT_IP_HEADER` in `render.yaml`. |
| The project page says the demo "has not answered for three minutes" | The service is failing to start | Read Render's **Logs**. |
| The project page still says "not online yet" after step 4 | The page in your browser is an older copy, or the workflow has not finished | Wait for the **Project page** run to turn green, then reload the page. |
| An answer is slow (over a minute) | The free instance has a fraction of one CPU; the cross-encoder is the slow step | In `render.yaml`, lower `TOP_K_RETRIEVAL` from 10 to 6, or set `RERANK_PROVIDER` to `none`, and push. |
